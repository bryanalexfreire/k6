Conclusiones del test de carga - Login (k6)

- Fecha de ejecución: 2025-12-17
- Duración del test: 25 minutos
- TPS objetivo: 20 TPS
- Iteraciones / requests totales: 30,000
- Umbrales configurados: p95 < 1500 ms; error rate < 3%

Hallazgos principales:
- Latencia: p95 de `http_req_duration` = 337.87 ms (p95 < 1500 ms) — UMbral de latencia CUMPLIDO.
- Throughput: tasa media de `http_reqs` ≈ 19.996 req/s (20 TPS objetivo alcanzado).
- Error rate: `http_req_failed` = 14.72% — UMbral de error NO CUMPLIDO (objetivo < 3%).
- Checks:
	- `response time <= 1500ms`: 30,000 passes (100%) — OK.
	- `status is 200`: 0 passes, 30,000 fails — indica que ninguna petición devolvió `200`.
	- Como hay 2 checks por iteración, `checks_total` = 60,000 con 50% passes (la mitad corresponde al check de latencia).

Interpretación:
- El servicio responde rápidamente (p95 ~338ms) y la prueba alcanzó la carga objetivo, por lo que la infraestructura puede soportar 20 TPS en términos de latencia.
- Sin embargo, un 0% de respuestas con `status 200` y una tasa de fallo aparente elevada indican que las peticiones de login no fueron exitosas (probable respuesta 401/400 o similar). Esto provoca que muchas solicitudes sean marcadas como fallidas por la aplicación o por el servicio remoto.

Posibles causas:
- Credenciales en `data/credentials.csv` no válidas para el endpoint de `https://fakestoreapi.com/auth/login` (autenticación rechazada).
- Formato del payload o headers diferente de lo esperado por el API.
- El endpoint podría estar regresando códigos de error intermitentes (logs del servicio ayudarán a confirmar).

Recomendaciones y siguientes pasos:
1. Verificar con el equipo o la documentación del API las credenciales válidas y el formato exacto del body esperado; probar manualmente con `curl` para confirmar un caso exitoso.
2. Repetir la prueba con al menos un conjunto de credenciales válidas dentro de `data/credentials.csv` para medir comportamiento en escenarios de login exitoso.
3. Capturar la distribución de códigos HTTP (200, 401, 500, etc.) para entender el motivo de las fallas. Ejemplo de comando para obtener códigos con k6 (añadir un `group` o registrar `res.status`):

	 - Reproducción rápida:
		 ```powershell
		 k6 run scripts/test-login.js --summary-export=summary.json
		 ```

	 - Sobrescribir duración (ej. 30 minutos):
		 ```powershell
		 setx DURATION "30m"
		 k6 run scripts/test-login.js --summary-export=summary.json
		 ```

4. Si el objetivo es probar carga con logins exitosos, asegurar que al menos X% (ej. 80-100%) de credenciales sean válidas; para probar tolerancia ante fallos, definir claramente la tasa esperada de errores y ajustar thresholds.
5. Revisar logs del backend para identificar razones de rechazo (autenticación, rate limiting, validación de payload).
6. Automatizar la recolección de códigos y agregar una métrica custom que cuente `status==200` para facilitar la visualización.
